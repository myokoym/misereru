# Documentation policy

このディレクトリの文書は、**内容の種類だけでなくライフサイクルで分離**します。

目的は、調査中のノイズ・現在有効な仕様・過去の意思決定を混在させず、プロジェクトが進んでも参照先を迷わない状態を保つことです。

## 現在の構成

```text
docs/
├─ README.md              # この運用ルール
├─ product/               # 現在有効な要件・仕様
├─ research/              # 未確定の調査・比較・検証
└─ adr/                   # 重要な意思決定と理由
```

### `product/`

**現在有効な状態だけ**を置きます。

- プロダクト要件
- 現在採用している仕様
- 現在の制約
- ユーザー体験上の前提

議論の履歴や落選案は置きません。

判断が変わった場合は、ここを現在の状態へ更新します。なぜ変えたかが重要なら ADR を残します。

### `research/`

**まだ決まっていないもの**を置きます。

- 技術比較
- 実験結果
- 候補比較
- 命名調査
- 未解決の論点

調査文書は結論だけでなく、再検討に必要な根拠・落選理由を残してかまいません。

ただし、確定済みの情報を恒久的に参照する場所にはしません。

### `adr/`

**採用した、または正式に提案している重要な意思決定**を1判断1ファイルで残します。

MADR (Markdown Architectural Decision Records) の考え方を採用します。

- <https://adr.github.io/madr/>

詳細な比較表や長い実験ログは ADR に複製せず、必要なら `research/` を参照します。

## Research のライフサイクル

調査が終わったら、次のように処理します。

1. **現在の要件・仕様に反映する内容**は `product/` へ反映する。
2. **後から理由を知る必要がある重要判断**は ADR を作る。
3. **調査詳細が将来も再利用できる**場合は research として保持するが、active index から外す。
4. **決定後は価値がほぼない一時的な比較**は削除してよい。履歴は Git に残る。

必要になった時点でのみ、解決済み調査の退避先として次を追加します。

```text
docs/research/archive/
```

**空の将来用ディレクトリは先に作りません。** 最初に実際の文書を置く必要が生じた時点で追加します。

### 例: 命名調査

名称が未確定の間は `research/naming.md` に候補・衝突・落選理由を残します。

名称が正式決定した後は、

- 現在の正式名は `product/` または README にだけ残す
- 命名判断を後から説明する必要があるなら ADR を作る
- 候補一覧自体に再利用価値があれば `research/archive/` へ移す
- 再利用価値がなければ削除し、Git 履歴に任せる

とします。

## ADR にする判断 / しない判断

ADR にする目安:

- レンダリング基盤の採用
- Markdown 方言・互換性方針
- 出力形式の基本方針
- 日本語組版エンジンの選択
- プロジェクト全体へ長期的な影響がある設計判断
- 後から「なぜそうしたか」を知る必要がありそうな判断

ADR にしないもの:

- 単なる候補一覧
- まだ比較中の調査
- 小さな実装詳細
- 容易に変更でき、判断理由を恒久保存する価値が低いもの

ADR は過去を書き換えて現在に合わせるのではなく、必要に応じて `Deprecated` / `Superseded` にし、新しい ADR から置き換えます。

## 将来のユーザー向け・開発者向け文書

実装が進み、実際に必要になった場合のみ、Diátaxis の考え方を参考に目的別ディレクトリを追加します。

想定例:

```text
docs/
├─ how-to/        # 特定の作業を達成する手順
├─ reference/     # CLI、設定、front matter、構文など正確な仕様
├─ tutorials/     # 初学者向けの段階的な学習資料
└─ explanation/   # 仕組み・背景・設計思想の説明
```

追加ルール:

- 必要な文書が1つもない段階ではディレクトリを作らない。
- 1文書に複数の目的を混ぜない。
- `reference/` に議論やチュートリアルを入れない。
- `how-to/` に設計判断の履歴を入れない。
- 重要な設計判断は、説明文書ではなく ADR を正本とする。

Diátaxis をディレクトリ規格として機械的に適用するのではなく、**文書の目的を混ぜないための分類原則**として使います。

- <https://diataxis.fr/>

## 文書を追加するときの判断順

新しい Markdown を作る前に、次の順で置き場所を決めます。

```text
現在有効な要件・仕様か？
  → product/

まだ比較・検証・探索中か？
  → research/

重要な意思決定と理由か？
  → adr/

利用者が特定作業を行う手順か？
  → how-to/（必要になってから作成）

正確なコマンド・設定・構文仕様か？
  → reference/（必要になってから作成）

段階的な学習資料か？
  → tutorials/（必要になってから作成）

背景や概念の説明か？
  → explanation/（必要になってから作成）
```

どれにも該当しない場合、既存文書への追記で足りないかを先に確認します。

## 基本原則

- **現在の正本と調査履歴を分ける。**
- **調査と決定を分ける。**
- **決定後に不要になった調査を通常導線へ残し続けない。**
- **空の将来用フォルダを先回りで増やさない。**
- **同じ情報を複数箇所で正本化しない。**
- **README は入口、詳細は役割別文書へ置く。**
- **履歴保存だけが目的なら Git 履歴も利用する。**
